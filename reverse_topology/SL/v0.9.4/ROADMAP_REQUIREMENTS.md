# План развития SINUMERIK/SINAMICS Monitor

## Исходные требования

Источник: `/root/req.txt`.

Цели проекта:

1. Read-only сбор NCK, SDB и SINAMICS.
2. Полная аппаратная топология: оси → CU → DO → Motor Module → датчики → DRIVE-CLiQ.
3. Однозначная связь логических объектов с физическим оборудованием, модулями, каналами и разъёмами.
4. Интерактивный веб-интерфейс на NiceGUI.
5. Циклический мониторинг, диагностика, события, история и данные для будущего ML.
6. Максимальное использование данных из ЧПУ без электрических схем, ручной конфигурации и жёстко заданной конфигурации конкретного станка.

## Оценка v0.9.4

| Требование | Состояние | Доказательство / ограничение |
|---|---|---|
| Read-only NCK/SDB/SINAMICS | Частично выполнено, сборочная часть подтверждена | S7 ReadVar, SDB Upload, отсутствие WriteVar/Download; 35 тестов проходят |
| Автоматическое обнаружение CU | Выполнено для проверенных снимков | CU определяются через MD13120; cnc135: 5 CU, cnc152: 2 CU |
| Чтение SDB | Выполнено | SDB 22/23 получены и декодируются; оба запуска имеют `COMPLETE` |
| Восстановление DRIVE-CLiQ | Выполнено для подтверждённых связей | cnc135: 58 рёбер, cnc152: 13; используется reciprocal-проверка портов |
| Оси → HW slot → CU/DO | Выполнено для проверенных снимков | cnc135: 19/19 осей подтверждены; cnc152: 6/6 |
| CU → DO → Motor Module | Частично выполнено | CU, DO и компоненты TLV есть; нужна единая семантическая модель связей и независимая валидация |
| Датчики/энкодеры | Частично выполнено | Servo references собираются, но нет полной доказанной цепочки до физического оборудования |
| Каналы и разъёмы | Частично выполнено | Селекторы портов проверяются; нет пользовательской модели разъёма и детального статуса каждого endpoint |
| Независимость от electrical/ARC | Сборщик не использует их как обязательный вход | Требование в целом соблюдается; ARC и схемы нужны для валидации, а не для восстановления |
| NiceGUI-интерфейс | Не выполнено | В v0.9.4 отсутствует web/UI слой |
| Циклический мониторинг | Не выполнено | Есть одноразовый capture и resume, но нет scheduler/monitor service |
| Диагностика событий | Частично выполнено | Есть журналы чтений и ошибок; нет нормализованной event-модели и severity |
| История / ML-ready данные | Не выполнено | JSONL capture не является версионированным временным рядом состояния |
| Расширяемая архитектура | Частично выполнено | Collector/model/decoder разделены; отсутствуют интерфейсы для monitor, storage и UI |

## Главный вывод

`v0.9.4` является рабочим read-only ядром offline-реконструкции и уже подтверждает значительную часть требований сбора и построения топологии. Полной системой мониторинга он пока не является.

Критические недостающие части:

1. единая доказательная модель полного пути `axis → CU → DO → drive module → motor/encoder`;
2. явная модель портов, разъёмов и степени уверенности связи;
3. циклический мониторинг состояния;
4. нормализованные события и история;
5. NiceGUI-интерфейс;
6. тесты на реальных снимках и cross-validation с ARC/электрическими схемами.

## Принцип модификаций

Сначала стабилизировать и расширить read-only ядро, затем добавлять мониторинг и UI. UI не должен содержать протокол, самостоятельно читать станок или восстанавливать связи. Все данные должны проходить через модель и слой состояния.

ARC и electrical используются для независимой проверки разработки и оценки уверенности. Они не становятся обязательной зависимостью runtime, поскольку основное требование — адаптация по данным самого ЧПУ.

# План этапов

## Этап A. Зафиксировать контракт ядра

Цель: превратить текущий экспериментальный формат в стабильный внутренний API.

Работы:

- выделить модели `Capture`, `ControlUnit`, `HardwareSlot`, `Axis`, `DriveObject`, `Component`, `Port`, `Connection`, `Evidence`;
- добавить обязательные поля `source`, `confidence`, `status`, `timestamp`, `raw_reference`;
- разделить `read_events`, `journal_events`, `array_events`;
- не менять существующие CSV/JSON без версии схемы;
- добавить schema version и collector version;
- сохранить совместимость с текущими `runs/cnc135` и `runs/cnc152`.

Критерий готовности:

- старые снимки пересобираются offline;
- существующие 35 тестов проходят;
- модель явно отличает `confirmed`, `probable`, `inferred`, `unresolved`, `contradicted`.

## Этап B. Усилить модель полной топологии

Цель: закрыть цепочку из требований проекта.

Работы:

- формализовать связи:
  - axis → logical drive;
  - logical drive → IO address/telegram;
  - IO slot → bus/slave;
  - bus/slave → CU/DO;
  - DO → Motor Module;
  - Motor Module → motor;
  - motor → encoder/sensor;
  - component port → peer component port;
- отделить физические кабели, typed relations и логические ссылки;
- добавить endpoint objects с номером группы, ordinal и selector;
- вынести `CU_LINK` в отдельный тип representation link;
- показывать причину каждой неподтверждённой связи;
- запретить автоматическое повышение уверенности при неполном TLV или неоднозначном индексе.

Критерий готовности:

- для каждого элемента цепочки есть ссылка на конкретные прочитанные адреса/поля;
- отсутствие данных приводит к `unresolved`, а не к догадке;
- offline-реконструкция обоих снимков сохраняет текущие 19/19 и 6/6 проверенных осей.

## Этап C. Cross-validation по cnc135/cnc152

Цель: проверить модель на двух разных конфигурациях.

Работы:

- построить нормализованные таблицы компонентов и связей для обоих станков;
- сопоставить компоненты по `device_id`, типу, bus/slave и контексту CU;
- отдельно классифицировать реальные отличия и ошибки реконструкции;
- исследовать `item_error`, одинаковые device IDs и повторные CU representations;
- извлечь из ARC параметры, идентификаторы и версии;
- извлечь из PDF независимый reference inventory;
- не использовать PDF/ARC для дорисовки runtime-графа.

Критерий готовности:

- по каждому расхождению указаны источники и уровень уверенности;
- есть отчёт, какие поля подтверждаются ЧПУ, ARC, схемой и декодером;
- выявлены конкретные пробелы текущей модели.

## Этап D. Read-only мониторинг

Цель: перейти от одноразовой выгрузки к безопасному циклическому опросу.

Работы:

- выделить `MonitorSession` поверх существующего `NckClient`;
- разделить редкие данные конфигурации и частые данные состояния;
- конфигурацию перечитывать по расписанию или по запросу;
- состояние осей/DO/ошибок читать циклическими пакетами;
- использовать bounded timeout, retry и backoff;
- обнаруживать изменение конфигурации и закрывать текущий snapshot;
- не смешивать состояния разных конфигураций;
- сохранить read-only запрет на уровне транспорта и тестов.

Критерий готовности:

- можно выполнить мониторинг без повторной полной топологии на каждом цикле;
- сбой связи не уничтожает предыдущую историю;
- смена identity/configuration создаёт новый snapshot.

## Этап E. События и история

Цель: подготовить данные для диагностики и будущего ML.

Работы:

- определить event types: connection, read failure, configuration change, axis state, drive state, alarm, topology change;
- добавить UTC timestamp, station identity, snapshot id, source address, old/new value;
- хранить сырые значения и нормализованные значения отдельно;
- использовать SQLite или Parquet/JSONL storage с ротацией;
- добавить агрегаты: availability, error rate, state duration, transition count;
- не смешивать диагностическое событие с обычным `item_error`.

Критерий готовности:

- историю можно читать по станции, snapshot, CU, оси и периоду;
- любое нормализованное событие восстанавливается до raw ReadVar evidence;
- данные имеют стабильную схему для ML-подготовки.

## Этап F. NiceGUI web-интерфейс

Цель: дать пользователю визуальный интерфейс уровня Topo для просмотра и диагностики.

Слои:

```text
NiceGUI pages
  → view models / queries
    → storage and current state
      → monitor service
        → read-only collector
```

Порядок UI:

1. список станков и состояние соединения;
2. обзор snapshot и полноты данных;
3. интерактивный граф DRIVE-CLiQ;
4. таблица CU/DO/modules;
5. таблица осей с цепочкой до оборудования;
6. карточка компонента и его портов;
7. unresolved/conflicts/errors;
8. timeline событий;
9. сравнение двух snapshot.

Требования к графу:

- физические кабели и логические связи разными стилями;
- цвет по типу компонента и состоянию;
- видимый confidence/status;
- переход от узла к raw evidence;
- отсутствие ложного соединения при неполном графе.

## Что не следует делать сейчас

- не дорисовывать связи по electrical или ARC;
- не переносить декомпилированный Siemens-код в проект;
- не строить UI непосредственно поверх `reads.jsonl`;
- не начинать циклический опрос до разделения конфигурационных и динамических данных;
- не объявлять `COMPLETE` только по успешному сетевому завершению без проверки полноты модели.
