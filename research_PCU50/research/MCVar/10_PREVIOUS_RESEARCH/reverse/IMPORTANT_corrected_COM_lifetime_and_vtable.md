# MCVar boundary consolidation and focused transport trace

## Outcome

Fresh objdump of original bytes resolves the immediate `0x10014CE2` dispatch as a CVar2 COM lifetime path, with two concrete static vptr candidates and their callees. It is not evidence of a request being submitted. The transport join remains unresolved. Existing research, binaries and runtime captures were not edited. Only this note and `research/logs_asmb/consolidation_architect.asm` were created.

## Evidence and recovered boundary

Primary new evidence: `../logs_asmb/consolidation_architect.asm`, generated by GNU objdump from the old PE's original .text bytes via anonymous memfd, avoiding export-label disassembly resets. The .text VMA is 0x10001000. The raw log includes reproduction commands, original .rdata words, and the new image's cleanup helper. Addresses below are preferred-image VAs, not observed runtime addresses.

1. The usable old body starts at **0x1000BC30**, with `push ebp; mov ebp,esp; sub esp,0x3c`. Export-labelled **0x1000BC74** is an interior `mov WORD PTR [edi],si`, not its prologue. At **0x1000BC3C**, `ebx=[incoming this]-0xc`; **0x1000BC45** calls **0x10014C8C**, passing `ebx`, literal 0xc and local address `[ebp-0xc]`.
2. **0x10014C96** stores that object pointer in wrapper `[edi+4]`. **0x10014C9E** invokes object slot +4. The helper increments `[[object+0x28]+0x4c]`, saves `[object+0x24]`, and temporarily sets that field to 0xc. Thus the later linked pointer originates in the adjusted CVar2 `this`, rather than a recovered CDdeAction allocation.
3. **0x1000BDDC -> 0x10014CBE**, with `ecx=&[ebp-0xc]` at **0x1000BDD9**, is epilogue cleanup. **0x10014CCB -> 0x10014CE7** decrements owner state. **0x10014CD5** restores object +0x24. **0x10014CDF** loads the object's vptr, and **0x10014CE2** executes `ff 50 08`, `call [eax+8]`, with the object pushed on the stack.
4. Concrete old vptr installs: **0x10008EE3** and **0x10009637** store **0x1002C5BC** at object +0xc. **0x100098D3** stores alternate **0x1002C758** at +0xc. Both tables contain the real body pointer **0x1000BC30** at slot +0x1c, at **0x1002C5D8** and **0x1002C774** respectively. This ties the incoming interface pointer, adjustment and lifetime dispatch together statically. It does not select which table the captured process instantiated.
5. For **vptr 0x1002C5BC**, slot +4 at **0x1002C5C0 = 0x100099CD**, whose thunk subtracts 0xc from stack `this` and jumps to **0x10009776** (increments object +0x18). Slot +8 at **0x1002C5C4 = 0x100099D7** subtracts 0xc and jumps to **0x10009783**, which decrements +0x18 and conditionally calls **0x10009620** and **0x100179D2**. These are concrete AddRef/Release-shaped bodies.
6. For **vptr 0x1002C758**, slot +4 at **0x1002C75C = 0x10009A63 -> 0x100098EE**; slot +8 at **0x1002C760 = 0x10009A6D -> 0x100098FE**. Both thunks adjust stack `this` by -0xc. **0x100098FE** loads controlling pointer `[adjusted this+0x18]`, and **0x10009908** calls its vptr +8. That controlling object's concrete vptr is the next unresolved lifetime edge; it is not yet a transport edge.
7. New-image **0x10014DC8** independently reproduces the cleanup helper; its actual indirect call is **0x10014DEC**. No blanket old/new relocation delta is inferred.
8. The other reported request-region dispatch is precisely **0x10004E2E**, `call [edx+4]`, following vptr load at **0x10004E25**, `ecx=esi` at **0x10004E29**, and pushes of 0 and dereferenced result. **0x10004E1D** is a direct call to **0x10007CAF**, not the indirect call. The concrete vptr and callee of 0x10004E2E remain unresolved.
9. Claimed constructor **0x1000E044** starts `lea eax,[ebp-0x30]` inside an existing stack frame. Export-labelled **0x100148B8** starts with trailing immediate bytes (`03 10`), followed by body code at 0x100148BA. Export names alone cannot establish these function entries or the asserted typed call graph.

## Focused next trace: concrete acceptance criteria

Priority is the data/request path, not further exploration of the lifetime wrapper. Perform offline backward slicing of **0x10004E2E** from **0x10004CA7**, track `esi`, enumerate every constructor/vptr store reaching it, decode the selected table's +4 entry, then follow that concrete callee. Likewise follow the real ReadVar body's **0x1000BD47 -> 0x1000C532** request-bearing candidate before using the export label for MakeCB. These are investigation targets, not proven submission edges.

For a future authorized Windows debugger run, first record loaded module bases and resolve the actual IDispatch/ReadVar vtable from the successful harness. Breakpoints must be base+RVA, not assumed absolute VAs. On the old build: body **MCVar+0xBC30**, main helper call **+0xBD47**, request-region vcall **+0x4E2E**, and lifetime discriminator **+0x14CE2**. At +0x4E2E capture thread, return stack, ECX/ESI, EDX, `[EDX+4]`, pushed arguments and object fields +0x14/+0x18/+0x24/+0x28/+0x30. Step into the resolved target and record its module and RVA. At +0x14CE2 capture vptr to distinguish the two recovered lifetime implementations; do not count this hit as transport.

Follow the actual outgoing API discovered from that callee: DDEML transaction and returned handle if present, or window-message/other IPC submission if present. Correlate service/topic/item, format, transaction arguments, thread/time and returned buffer with the single harness invocation. On ncdde, static report candidates **0x448AC0**, **0x44A730**, **0x44AD50** and **0x44AE23** require module-base adjustment and fresh verification before setting breakpoints; they were not re-disassembled in this timeboxed audit. Record serializer input/output buffer and API handle, then compare exact bytes to the capture. Do not infer shared addresses across processes.

Accept the bridge only with a selected vptr/callee plus actual submission and server/buffer correlation. If direct DDE-only runs change +7 without MCVar, that falsifies exclusive MCVar ownership; it does not identify the writer. No live runtime was started in this audit.
