# Cyclic data-flow and subscription lifecycle

## Scope and evidence rules

Offline static analysis of the supplied old and new `MCVar.dll` images only. No Windows tooling/execution, DDE, collector, or binary modification. The stage16.5 lifecycle labels are treated as hypotheses; decorated names and diagnostic strings do not by themselves prove call edges. The follow-up raw-byte evidence is in `/root/PL/stages/stage16_5/cyclic_flow/followup/STAGE16_6_CYCLIC_CAUSAL_EDGES.md`; source inventories are `stage16_5/evidence/rizin_{old,new}_async_cyclic_strings.txt`.

Old image: `/root/PL/PCU_old/H/mmc2/MCVar.dll`, PE32 i386, preferred base `0x10000000`, built 2004-06-23. New image: `/root/PL/PCU_new/C/RECYCLER/S-1-5-21-4025392478-4199590385-3038547483-1005/Dc28/files/F/mmc2/MCVar.dll`, PE32 i386, preferred base `0x10000000`, built 2011-07-25. The detailed object/call evidence reproduced here is explicitly per version below.

Evidence labels: **DIRECT** means an instruction-level direct relative call or an operand/data access verified in raw x86 bytes; **INFERRED** means independent static evidence supports a relationship but not the exact causal instruction; **UNRESOLVED** means the proposed edge/state transition is not established. Type library method declarations prove exposed API shape only, not internal behavior.

## Reconstructed lifecycle

1. **Public subscription request.** Both TypeLibs expose `ReadVarCyclic` (memid 5) and `RemoveCyclicVariables` (memid 6) on `IVar`/`IVar2`; `ReadVarCyclic` accepts subscription inputs including names/handles, callback or dispatch sink, deadband and requested/revised update rates, and outputs a `ReqID` (`stage16_5/abi/README.md` and `typelib_abi_records.json`). Both images contain implementation diagnostics for `IVar::ReadVarCyclic`, `IVar2::ReadVarCyclic`, request IDs, `StartCyclic`, and variable record creation. This establishes that cyclic request and record concepts exist; it does not prove an exact call sequence or rollback behavior.
2. **Ownership model.** Diagnostics name `CCyclicID/ReqID` allocation/free and `CCyclic` allocation/free. `StartCyclic` diagnostics include RID, variable name, critical flag, server/client handles and requested update rate; record creation diagnostics add deadband. This supports a request-ID-level owner and per-variable cyclic records. Actual ID allocation/reuse, whether every request creates a fresh ID, list insertion order, and record-to-owner pointer field are unresolved.
3. **Data/change path.** Both builds contain `CCyclic::Data(change,id)` and `CCyclicID::DataChange`; DataChange diagnostics mention `tag`, `susp` and pending count, plus `Change` and `hotR`. Those strings establish relevant concepts in implementation, but not exact field offsets or the code that writes pending state. Therefore `CCyclic::Data -> DataChange`, pending/coalescing semantics, and suspension gating are **inferred or unresolved**, not direct call facts.
4. **Idle and flush path.** `IdleCB` and `FlushCyclics` diagnostics/symbol labels exist in both images. However, the candidate IdleCB labels begin at bytes that disassemble implausibly, and symbol boundaries overlap a larger region. A Capstone scan of `.text` found no direct relative call to the listed DataChange/IdleCB/FlushCyclics symbol VAs. This cannot exclude virtual/function-pointer calls, but it means `DataChange -> IdleCB -> FlushCyclics` is unresolved. Do not claim a timer, thread, or callback cadence; timer API imports do not prove cyclic ownership.
5. **Flush list processing.** Raw instructions in both versions show `FlushCyclics`-region logic loading an owner list head from `[this+0x0c]`, following node `next` at `node+0`, reading the candidate object pointer at `node+8`, and then accessing the candidate cyclic record at offsets `+0x74`, `+0x38` and `+0x40`. This is the corrected, deliberately partial object layout; it does not establish a complete struct, field meanings, or object size. The old label entry at `0x10012d7f` itself is not a trustworthy function start, so refer to this as the FlushCyclics-region pattern rather than treating its symbol prologue as validated.
6. **Callback-shaped dispatch.** In the new image, at `0x100134ab`, a conditional branch path in the FlushCyclics region directly calls `0x100139c2`; the condition tests mask `0x80000` at owner `[this+0x28]`. The target helper contains `OnDataChanged` and `OnWriteComplete` dispatch diagnostics, so its role as a general callback-dispatch helper is supported. This proves the direct call and its guarding condition, not that this invocation dispatches `OnDataChanged`, which interface slot it invokes, or the exact meaning/order of its six pushed arguments. No equivalent old-build cyclic caller edge is established; old helper `0x100138b8` has callback-dispatch evidence, but a cyclic caller was not verified.
7. **Removal and controls.** TypeLib declarations expose `RemoveCyclicVariables(ReqID, Names, ServerHandles, errors)` (IVar2 also accepts ClientHandles), `Cancel`, `Suspend`, and `Resume`. Implementation strings include `Invalid ReqID`, removal diagnostics, and `free CCyclic`/`free CCyclicID/ReqID`; a named `CCyclicID::Delete(CCyclic*)` was previously identified. This supports request- and variable-scoped management and object destruction as concepts, but direct removal-to-delete calls, match precedence, empty-input behavior, last-record owner destruction, and Cancel/Suspend/Resume transitions are unresolved.

## Corrected conclusion

The complete sequence `data arrival -> DataChange -> pending -> IdleCB -> FlushCyclics -> OnDataChanged` is **not established**. Strongest proven endpoint is the version-independent list/object access pattern in the FlushCyclics region, plus a new-build conditional direct call from that region to a callback-dispatch candidate helper. Subscription creation, deletion and state-management semantics remain only partially reconstructed. See `CYCLIC_OBJECT_LAYOUT.json` for byte-level fields and `CYCLIC_FUNCTION_GRAPH.json` for edge status and addresses.
