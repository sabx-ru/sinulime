# Stage 16.5 Corrections

## Correction A: `+0x14` is `IDispatch::GetIDsOfNames`

The previous Stage 16.5 wording that treated the call at old `0x1000fef1` / new `0x10010003` as direct `OnDataChanged` delivery is **SUPERSEDED**.

Verified old callsite bytes/instructions:

```asm
1000fed3: 8b 07                mov eax, [edi]
1000fed5: 8d 4d 14             lea ecx, [ebp+0x14]
1000fed8: 51                   push ecx              ; rgDispId
1000fed9: 68 00 08 00 00       push 0x800             ; LCID
1000fede: 8d 4d 10             lea ecx, [ebp+0x10]
1000fee1: 6a 01                push 1                 ; cNames
1000fee3: 51                   push ecx              ; rgszNames
1000fee4: 68 c8 d6 02 10       push 0x1002d6c8        ; riid pointer
1000fee9: 57                   push edi              ; IDispatch this
1000feea: c7 45 10 cc 20 03 10 mov [ebp+0x10], 0x100320cc
1000fef1: ff 50 14             call [eax+0x14]
```

The call arguments match `IDispatch::GetIDsOfNames`, whose vtable slot is `+0x14`, not `IDispatch::Invoke` (`+0x18`). The old string at `0x100320cc` is UTF-16 `OnDataChanged`; the new binary has the corresponding string at `0x1003311c`. Both name-resolution callsites pass LCID `0x800`, one name, and a zeroed GUID pointer consistent with `IID_NULL`. The `rgDispId` output is a stack local, but subsequent use as the DISPID argument to a proven `Invoke` has **not** been established.

The old path checks the `GetIDsOfNames` HRESULT at `0x1000fef4` and branches on failure. A separate callback routine contains a later `IDispatch::Invoke`-shaped call at old `0x100146a0` / new `0x100147aa`; nearby diagnostics log `Dispatch "OnDataChanged" called` and returned HRESULT. This is static dispatch evidence, not runtime callback success. The exact per-request edge remains unresolved.

## Correction B: method count definition

The prior statement `33 methods across eight target TypeInfos` is **SUPERSEDED** for the direct-function count.

Recomputed from `/root/PL/stages/stage16/reports/typelib_decode.json`:

| TypeInfo | Direct `funcs` records |
|---|---:|
| `IVar` | 12 |
| `IVar2` | 12 |
| `IReadVarAsyncCallback` | 1 |
| `IReadVarAsyncCallback2` | 1 |
| `IWriteVarAsyncCallback` | 1 |
| `IWriteVarAsyncCallback2` | 1 |
| `IMCCommand` | 3 |
| `IMCCommandAsyncCallback` | 1 |
| **Total** | **32** |

There are 28 TypeInfos in each decoded library and 92 direct function records across all TypeInfos. The eight target TypeInfos contain 32 direct function records: `12 + 12 + 1 + 1 + 1 + 1 + 3 + 1`. All eight targets are `TKIND_DISPATCH` and each has an `IDispatch` impltype reference, but inherited `IUnknown`/`IDispatch` slots are not materialized in the target `funcs` arrays and are deliberately not added. Adding the full four inherited `IDispatch` methods per target would produce 64, not 33; adding one arbitrary inherited slot is therefore not a valid explanation for 33. No property getter/setter duplication, duplicate memids within a target, or target variables were observed. `memid` values may repeat across separate interfaces; this does not create additional direct records.

The `33` originated in the Stage 16.5 prose/test-result summary, not in the preserved per-interface records: `typelib_abi_records.json` has the same 32 function entries as the raw decode for each revision. Thus 33 is an off-by-one reporting/counting error with no corresponding extra descriptor, inherited slot, property accessor, or duplicate memid. The canonical comparison remains 8 target TypeInfos with zero changed normalized records. The corrected count is recorded in `corrections/counts/method_count.json` and generated by `corrections/counts/recount_typelib.py`.

## Correction C: function boundaries

Automatic labels are not accepted as proof of independent function boundaries.

- `ReadVarAsync` entry addresses `old 0x1000d28a` and `new 0x1000d39c` are retained as implementation entry candidates because raw bytes, entry metadata, direct call context, and old/new structural equivalence agree. The 30-byte entry span is verified directly against both PE images.
- The legacy labels `old 0x1000d3f6` and `new 0x1000d508` begin inside the larger transaction body and are **not** accepted as independently verified forwarding thunks.
- The decorated `DataChange` and `IdleCB` labels have implausible/misaligned bytes in both builds and remain analysis-boundary labels only. Their bodies and causal edges are not promoted.
- `FlushCyclics` list-loop accesses and the new-build direct call at `0x100134ab -> 0x100139c2` remain local byte-level evidence, not proof that every symbol label is a clean function start.

The corrected machine-readable boundary map is `corrections/boundaries/corrected_function_map.json`; `corrected_function_boundaries.json` is an earlier provisional map and is superseded by that validator-backed record.
