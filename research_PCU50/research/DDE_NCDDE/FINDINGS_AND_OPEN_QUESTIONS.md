# DDE/NCDDE — подтверждённые факты и нерешённые вопросы

## Двоичный формат — OBSERVED_RUNTIME

Оригинальные кадры находятся в `experiments/pcu_baseline/raw/` и `experiments/pcu_phase14/raw/`:

- Первый прогон: **198** `*_binary.bin`, **69** `*_text.bin`. Второй прогон: **579** `*_binary.bin`, **396** `*_text.bin`. Каждый двоичный кадр выдержал проверку длины заголовка 20 байт, версии 1, `F9 F8 F7 F6` по `+0x10` и длины полезной части по `+0x0C`.
- Наблюдаемый однобайтовый `sequence` расположен по `+7`; заголовок смешивает тип и состояние в прочих полях. Внутри второго прогона `(WORD+4, BYTE+6)` встречаются `(1,2)` — 311, `(1,3)` — 12, `(2,5)` — 116, `(100,6)` — 140.
- **Нельзя** определять восьмибайтовый payload `(100,6)` как BCD-время только по длине. Сохраняемый `tools/phase12/ncdde_capture_parser.py` имеет такую ошибочную эвристику; пользуйтесь `tools/capture_reader.py`. Для однозначного типа требуется адрес/метаданные.
- `CF_OEMTEXT=7` — не номер элемента `7`. Специальная ветка работает только после сравнения DDE item handle; по конкретному special item выдаёт `Ncdde\0` (6 байт). Отказы обычных OEM-запросов не опровергают существования этой ветки.

## Общий sequence — CORRELATED, не доказанный сетевой transport

В Phase14 после совмещения хронологической последовательности ответов наблюдались **578/578** переходов, согласованных с `delta_seq = (1 + принятое число MCVar элементов между ответами) mod 256`. В серии Q — 16 обычных совпадений и одно отклонение `SAFEARRAY(VARIANT)` без обработки элементов. Реальный корпус и журналы доступны для независимой реконструкции. Это говорит о совместимом состоянии сервера, **не** о числе TCP/NCU транзакций и не о доказанном прямом вызове MCVar→DDE. Счётчик 8-битный; полные обороты и сторонние запросы невозможно исключить одной арифметикой.

## Дизассемблирование старого `ncdde.exe` — PROVEN_STATIC

Приоритетный источник: [`reverse/IMPORTANT_corrected_serializer_counter_and_OEM.md`](reverse/IMPORTANT_corrected_serializer_counter_and_OEM.md), затем `reverse/annotated_ncdde_old_serializer.md` и `reverse/phase12_serializer_trace.md`.

- `0x448AC0` — обработчик `XTYP_REQUEST`; `0x449265…0x4492D3` — выбор `CF_TEXT`, зарегистрированного формата, `CF_OEMTEXT` и сравнение item.
- Путь normal serializer `0x44A440 → 0x40203B → 0x44A730`, с глобальным буфером вывода B=`0x486BD0`; при разрешённой ветке `0x44AAA3` пишет byte `B+7` из глобального состояния `0x486884` и обновляет это состояние.
- Путь создания DDE handle: `0x44A680 → 0x4012F8 → 0x44AD50 → 0x44AE23 → 0x466F56 → DdeCreateDataHandle`; отдельная ветка добавляет данные через `DdeAddData`.
- Нельзя приписывать `0x85000903` найденной внутренней функции: **конкретное происхождение ошибки не доказано**. Старый MCVar `0x10007CAF` / новый `0x10007DBD` демонстрируют cleanup, не DecodeError.
- Нельзя утверждать, что нулевой byte находится в самой PE на `0x486884`: адрес лежит в виртуально инициализируемом хвосте `.data`, не в file-backed `.data`.

Адреса относятся к старому конкретному образу (хеш в `reverse/old_ncdde_exe_sha256.txt`), не являются универсальными RVA и **не доказывают** соответствие каждого сетевого/runtime пакета этому сериализатору без корреляции входов/выходов. `reverse/raw_disassembly_and_xrefs.tar.gz` содержит оригинальные машинные данные, чтобы не повторять анализ.

## Следующие адресные задачи

1. Соотнести один конкретный COM `ReadVar` → IPC/DDE event → NCDDE `XTYP_REQUEST` → ответный handle/buffer на одной PCU.
2. Определить независимые границы пакета/элемента и фактический уровень COTP/TCP к NCU без предположения по одному счетчику.
3. Разделить BCD/time и строку по реальным metadata/серверному типовому дескриптору.
4. Выяснить сброс, конкурентность и границы переполнения `sequence`, а также неопределённое машинное время `SysTimeBCD`.
